- (decision) Form-factor resuelto: escritorio Windows 10/11 (NFR-4), dos aplicaciones distintas, Servidor y Cliente (PRD §3, Vision). Avalonia es la hipotesis de stack del plan maestro, no una decision de Fase D; la UX se define a nivel de comportamiento de escritorio, sin depender de un UI kit concreto.
- (decision) Superficie unica por aplicacion, sin multi-surface. No hay breakpoints responsive: el cliente y el servidor son aplicaciones de escritorio de tamano de ventana variable. Responsive & Platform no se dispara por breakpoints, pero si se documenta el comportamiento de redimensionado de escritorio en la seccion Responsive & Platform.
- (decision) Sin sistema de componentes de UI nombrado en el PRD. La UX define su propia capa de componentes, por lo que DESIGN.md specify tokens propios en lugar de heredar de un design system externo.
- (decision) Idiomas de la interfaz: espanol, coherente con document_output_language y con la documentacion del proyecto. Los identificadores de codigo, tokens, nombres de componente y contratos tecnicos van en ingles.
- (decision) Nombres de protagonistas tomados literalmente del PRD: Ana (jugadora de LAN), Luis (organizador del evento), Marta (administradora del servidor). Se respetan sus nombres de journeys UJ-1, UJ-2 y UJ-3.
- (decision) Cobertura MVP (contrato de Fase C): descubrimiento y conexion al servidor, compatibilidad de version de clientes, catalogo, detalle de videojuego, descarga con progreso/pausa/reanudacion/errores, instalacion portable, lanzamiento, y estados/errores/recuperacion. Cubre las siete pantallas de cliente que el plan maestro pide en Fase C mas los flujos minimos de administracion del servidor.
- (decision) Compatibilidad de version (FR-4): NO existe autenticacion ni autorizacion de clientes. La UI muestra un estado de version del cliente frente a la version del servidor, un diagnostico explicito cuando es incompatible, y permite consultar la version requerida o disponible. El cliente incompatible no inicia sincronizacion, descarga ni instalacion.
- (constraint) Integridad y autenticidad de paquetes (FR-6) y manifiestos (FR-8) se conservan como RESTRICCIONES, no como implementacion. La UX diseña el comportamiento observable: estado de validacion, diferenciacion de corrupcion frente a no confiable, rechazo antes de instalar, confirmacion explicita para operaciones privilegiadas, proteccion contra extraccion fuera del directorio autorizado y rechazo de manifiesto manipulado. La raiz de confianza, su distribucion, el algoritmo y el formato de firma NO se deciden aqui (OQ-1, Fase D).
- (constraint) Mecanismo de descubrimiento (R3, OQ-2) NO se decide. La UX diseña dos vias de acceso visibles y equivalentes: descubrimiento automatico y direccion manual introducida por el usuario. El mecanismo concreto es decision tecnica de Fase D.
- (constraint) P2P (OQ-3) NO se decide y NO se presenta como capacidad disponible. La UI del cliente muestra descarga desde el servidor; el intercambio entre peers no aparece en la interfaz del MVP.
